# Changelog

Date: 2 November 2026

The changelog of the `flow` plugin. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). The rules are in `plugins/flow/reference/WORKFLOW.md` section 12.

## [Unreleased]

### Added
- `/flow:release` makes a release in the way of the project. Its first run talks the release through with the developer, and writes a recipe to `docs/workflow/RELEASE.md` through a pull request. Later runs follow the recipe, and `/flow:release setup` changes it. A project with a config can add the line `Release: none` under "Records". Task: [0013-release-skill](docs/tasks/_archive/0013-release-skill/BRIEF.md).

## [0.1.0] - 2026-11-07

### Added
- The `flow` plugin, version 0.1.0, extracted from the workflow of an earlier project. It has the skills `adopt`, `discuss`, `plan-task`, `implement-task`, `checklist`, `finish-task`, `whats-next`, `tutorial` and `release`, and the `step-builder` agent. The settings of each project are in `docs/workflow/CONFIG.md`. The plugin supports the git models `trunk` and `git-flow`, the hosts `github` and `azure-devops`, and the optional tracker `azure-boards`. Task IDs, the changelog style and branch protection are settings, so that a team can use it. See [docs/DESIGN.md](docs/DESIGN.md).
- This repository as a marketplace, with its own workflow config, verify script and git hooks.
- `/flow:adopt` starts with a quick setup. It reads the base branch, the host, the repository and the verify command from the project, sets every other setting to a default, and shows them in one block to accept. The full conversation stays available. `README.md` explains how to test the plugin from a copy with `claude --plugin-dir`. Task: [0002-quick-setup](docs/tasks/_archive/0002-quick-setup/README.md).
- `/flow:roadmap` turns client requests into a roadmap of milestones in `docs/roadmap/`. Each milestone holds short cards, an order and an optional target date. The repository keeps a summary of each request, never the raw text. `/flow:discuss <card title>` turns a card into a brief, and the task file names its card. `/flow:whats-next` derives the progress per milestone from the archived tasks, and suggests the next card that can start. Task: [0007-roadmap-skill](docs/tasks/_archive/0007-roadmap-skill/README.md).
- `bench/` holds a benchmark of the workflow. It has a TypeScript sample project that is set up for `flow`, a pilot feature with hidden tests, a Python driver and a report. The driver runs Claude Code headless on a copy of the sample project and plays the developer. The report compares the setups `lean`, `flow-inline` and `flow-agents` on cost, quality and workflow. A `.gitattributes` file keeps LF line endings for shell scripts and git hooks. Task: [0010-benchmark](docs/tasks/_archive/0010-benchmark/README.md).
- The benchmark has the setups `flow-inline-fresh` and `flow-agents-fresh`. They start a new Claude Code session at each `/flow:` command. `bench/RESULTS.md` holds the results of the 15 runs of the feature `holds`. Task: [0011-fresh-sessions](docs/tasks/_archive/0011-fresh-sessions/README.md).

### Changed
- The core of the workflow needs only a base branch, one feature branch per task and a pull request. It uses plain `git`, so it works in any project. Git hooks and `/flow:release` are optional extras. A project with a config removes the settings "Model" and "Branch protection", and sets "Host" to `github`, `azure-devops` or `other`. Task: [0001-minimal-git](docs/tasks/_archive/0001-minimal-git/README.md).
- The core of the workflow is the loop from discuss to pull request, with a guarded base branch. The git hooks are always on, and `pre-push` refuses every push to the base branch. `/flow:release`, the `fragments` changelog, Azure Boards, the `work-item` task ID, extra records and milestones are removed. A project can add them back as project rules or project skills. A project with a config must remove "Tracker", "Extras", "Extra records" and the `Milestone` line. It must change `fragments` to `direct` or `none`, and `work-item` to `number` or `slug`. It must copy the hooks of the plugin to `tools/git-hooks/`, and run `git config core.hooksPath tools/git-hooks` in each clone. Task: [0003-standalone-core](docs/tasks/_archive/0003-standalone-core/README.md).
- `/flow:checklist` opens a review page in the browser. The developer marks each item as passed or failed, and can add a comment. "Finish" returns the results to the agent. Without Python 3, the page downloads a result file. Without a browser, the developer replies in prose. A comment on a passed item becomes a `Note:` line. `/flow:discuss` and `/flow:adopt` have no limit on questions per round, and ask the questions with the most impact first. Task: [0004-review-page](docs/tasks/_archive/0004-review-page/README.md).
- Each icon of the workflow output has one meaning. A message that waits for the developer ends with one 👉 line, and a session summary ends with one ▶️ line. Discovery questions stand in a "❓ Questions" section, with ● on the default answer. 🧠 is removed, and ❓ and 📁 are added. The verify script fails on an icon outside the set. Task: [0005-streamline-icons](docs/tasks/_archive/0005-streamline-icons/README.md).
- The config has a section "Testing". "Rule" sets which code gets automated tests: `none`, `critical` or `logic`. "Types" names the test types of the project, each with its meaning and an optional command. `/flow:adopt` proposes both from the tests of the project. `/flow:plan-task` plans each test with its code, type and reason, and asks before it adds a test for an untested function that the task changes. An optional "Coverage" command reports the coverage of the changed lines in `/flow:finish-task`. It never blocks. A project with a config moves its testing rule from "Project rules" to the "Testing" section, and adds "Coverage" under "Commands", or `none`. Task: [0006-configurable-tests](docs/tasks/_archive/0006-configurable-tests/README.md).
- The workflow uses fewer tokens. A task picks `agents` mode only by its number of steps. Each skill reads only the sections of the workflow guide that it cites. `/flow:adopt` and `/flow:tutorial` still read the whole guide. `/flow:plan-task` always reads the scope document and the decision log, and the other documents of the config only when the task touches them. The workflow guide says that a small fix is done outside the loop, on its own branch and through a pull request. The verify script checks that every cited section of the workflow guide exists. Task: [0008-token-use](docs/tasks/_archive/0008-token-use/README.md).
- The workflow reads and writes less text. `AGENTS.md` no longer tells the agent to read the whole workflow guide. Each skill and the step builder skip a file that the session already holds and did not edit. The pull request of `/flow:finish-task` drops the steps table, the choices and the changelog entry. `/flow:finish-task` checks the writing style `ste` with a script of the plugin, when Python 3 is installed. `/flow:plan-task` checks that each step passes the verify command at its own end. A project with an `AGENTS.md` from the template changes the row of the workflow guide in "Read these first". Task: [0009-read-once](docs/tasks/_archive/0009-read-once/README.md).
- The loop has two skills. `/flow:discuss` writes a brief with a map, parts and a human checklist. `/flow:build` builds the brief on autopilot in a new session and opens the pull request, with the human checklist in its description. `/flow:plan-task`, `/flow:implement-task`, `/flow:checklist`, `/flow:finish-task`, agents mode, the step builder and the review page are removed. Each skill holds its own rules. A project with a config removes "Mode threshold" from "Tasks". It changes "the current step" to "the brief" in hard rule 1 of its `AGENTS.md`. It finishes its active tasks with the old version first. Task: [0012-thin-flow](docs/tasks/_archive/0012-thin-flow/README.md).
